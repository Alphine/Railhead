Railhead

01 / Context

01Overview

Railway's template hub lists 517 "starter" templates. Framework starters (bare Node.js, Django, Flask) dominate by deploy count, but the moment a builder wants a real SaaS — auth, billing, transactional email, background jobs — the field thins out fast. The top result, Open SaaS, sits at 323 deploys but locks users into the Wasp meta-framework. Everything else stalls under 50 deploys and stitches together at most two of the five pieces a production SaaS actually needs.

None of the existing templates reach billing, and none lean on the one structural advantage Railway has over Vercel-style platforms: a long-running worker process. That's the gap this template fills.

Thesis — ship the two hardest, most-skipped pieces (Stripe billing and a real background worker) already wired up, on plain Next.js, so nobody has to learn a new framework to get a working SaaS skeleton.

02 / Scope

02Goals & non-goals

Goals

  • One-click deploy that produces a working sign-up → subscribe → receive-email loop with zero code changes.
  • Every required secret validated at boot; a missing key fails loudly with a named remediation, not a silent 500.
  • Background work (email sending, webhook processing) never blocks a request thread or a Stripe webhook response.
  • Plain, unopinionated Next.js — no custom CLI, no DSL, no meta-framework lock-in.

Non-goals

  • Multi-tenant / organizations data model — v1 is single-user-per-account, noted as a v2 extension point.
  • Admin dashboard UI beyond a minimal job-inspector page.
  • Support for payment providers other than Stripe, or email providers other than Resend, at launch.
03 / Audience

03Target user

An indie developer or small team who already knows Next.js, has an idea worth charging for, and doesn't want to spend the first week wiring auth and Stripe again. They've likely tried a Vercel-oriented kit before and hit its ceiling the moment they needed a cron job or a queue that outlives a serverless invocation.

04 / System

04Architecture

Four Railway services, two of them managed plugins. web is the only service with a public port; worker talks to Postgres and Redis only, over Railway's private network, and is scaled independently of request traffic.

07 / Sequences

07Core flows

Auth

  1. Visitor requests a magic link or submits a password on /sign-in.
  2. Better Auth validates against users / accounts via the Drizzle adapter.
  3. Magic-link path: web enqueues a send-magic-link job to Redis instead of calling Resend inline.
  4. Worker consumes the job, calls Resend, writes the result to jobs_log.
  5. On success, a session row is created and a signed, httpOnly cookie is set.

Billing

  1. User picks a plan; web creates a Stripe Checkout Session server-side and redirects to Stripe.
  2. Stripe hosts the payment form; on success it redirects back to /billing/success.
  3. Stripe fires checkout.session.completed and customer.subscription.updated to /api/webhooks/stripe.
  4. Web verifies the signature, returns 200 immediately, and pushes the raw event onto Redis — Stripe's 5-second timeout is met no matter what the worker is doing.
  5. Worker consumes the event, upserts subscriptions, and enqueues a send-receipt email job.

Background jobs

  1. Either service enqueues through a shared @app/queue package wrapping BullMQ.
  2. Worker is a dedicated Railway service — no public port, scaled by queue depth, not request volume.
  3. Failed jobs retry three times with exponential backoff, then land in a dead-letter queue visible on /admin/jobs for manual replay.

09 / Delivery

09Repo & deployment topology

Single monorepo, two Railway services pointed at different root directories:

  • /apps/web — Next.js app, Railway service web
  • /apps/worker — BullMQ consumer entry point, Railway service worker
  • /packages/db — Drizzle schema + migrations, shared by both services
  • /packages/queue — BullMQ queue and job-type definitions, shared
  • /packages/email — React Email templates, imported by the worker

Postgres and Redis are attached as Railway-managed plugins and wired in via reference variables (${{Postgres.DATABASE_URL}}, ${{Redis.REDIS_URL}}) declared in the template's railway.json — nobody copy-pastes a connection string by hand.

10 / Hardening

10Security

  • Stripe webhook signature is verified before any database write; the raw request body bypasses Next.js's JSON body parser so the signature check is against untouched bytes.
  • Session cookies are httpOnly, secure, and sameSite=lax; BETTER_AUTH_SECRET rotates through a Railway variable redeploy, never hardcoded.
  • Public networking is disabled on both the Postgres and Redis plugins by default — only web and worker can reach them, over the private network.
  • Sign-in and magic-link endpoints are rate-limited with a Redis token bucket to blunt credential stuffing.
  • The worker exposes no HTTP port, so it carries no public attack surface at all.
